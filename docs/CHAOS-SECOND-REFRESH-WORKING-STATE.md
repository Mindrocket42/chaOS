# chaOS second refresh — working state

Date: 2026-10-30
Branch: `chaos-core-second-refresh`
Baseline: `chaos-core-first-refresh` at `1fff35f829dde23e20d33f1028908a153510c88d`

## Objective

Strengthen chaOS as an execution and evidence boundary without importing Chat On Steroids' product/runtime sprawl.

The second refresh keeps the first-refresh rule intact:

> ChatGPT decides. chaOS executes. Receipts prove what happened.

## Scope accepted from current Chat On Steroids

1. **Caller provenance** — local actions should carry transport-generated attribution rather than model-supplied identity.
2. **Evidence-rich receipts** — successful mutations should return machine-verifiable facts, not only `ok: true`.
3. **Fail-closed ambiguity** — when the bridge cannot establish the action's local caller context, mutating actions should not silently proceed.
4. **Idempotency discipline** — duplicate action ids must not produce a second mutation inside one host lifetime.
5. **Capability fingerprinting** — health should expose a stable fingerprint of the currently granted local execution surface so ChatGPT can detect permission/root changes.
6. **Verification tests** — the above invariants belong in the native-host test suite.

## Explicit exclusions

Do not import:

- Goal / Loop;
- worker chats or worker lifecycle;
- automatic Continue / turn rotation;
- ChatGPT tab scheduling or recovery;
- conversation recording as execution state;
- a local agent framework;
- UI/product features unrelated to the capability kernel;
- browser DOM state as the source of truth for local execution.

## Implementation plan

### A. Transport-generated caller context

The extension background script derives caller context from Chrome's `sender` object and forwards only that generated context to the native host. Model output cannot choose or overwrite it.

Minimum context:

- surface (`chatgpt-tab`, `extension-page`, `unknown`);
- tab id when Chrome supplies one;
- frame id;
- origin/host classification, not raw sensitive URLs.

### B. Native receipt envelope

Every completed call returns receipt metadata alongside the action result:

- receipt schema version;
- action;
- request id;
- caller context;
- started/finished timestamps;
- duration;
- capability fingerprint.

The result payload remains action-specific.

### C. Mutation evidence

For `fs.write` and `fs.replace`, return:

- resulting byte count;
- resulting SHA-256;
- whether the file was created where applicable;
- replacement count where applicable.

This makes the receipt independently checkable by a later `fs.read`/hashing pass and prevents `ok: true` from being mistaken for evidence.

### D. Mutating-call attribution gate

The host refuses write/process mutation actions that arrive without caller context generated by the extension. Read-only health/read/search may remain available for diagnostics.

This gate is transport policy, not conversation identity. chaOS does not attempt to infer or persist ChatGPT conversation ownership.

### E. Tests

Add tests proving:

- health capability fingerprint is stable for unchanged config and changes when capabilities/roots change;
- mutating calls without caller attribution fail closed;
- a write receipt includes the resulting SHA-256;
- duplicate successful action ids do not execute twice inside the same host lifetime;
- caller metadata is reflected in the receipt and cannot be supplied through action args.

## Working findings

- First refresh already starts closed: no roots and all capabilities disabled.
- Request ids already have an in-memory successful-call cache, which is the correct base for same-host idempotency.
- The extension currently forwards only `{id, action, args}`; there is no caller provenance in the native protocol.
- `fs.write` / `fs.replace` currently return mutation counts/bytes but no content digest.
- `health` reports roots/capabilities but has no stable fingerprint for detecting a changed local authority surface.
